# 検証台（bench）— 測れる台の設計

`script/bench/`。生成済み応答へ機械軸を当てて**不良を落とす**ための台。
なぜ在るか、何を禁じとるか、どう使うかを1枚に置く。実測値は
[bench-conditions-2026-09-01.md](bench-conditions-2026-09-01.md) 側。

## なぜ作ったか

7ヶ月改善しても品質が上がらんかった。原因は改善やのうて**測定**で、上がったか下がったかを
判定できとらんかった。根拠にした数字が毎回あとで崩れる（過去スコア 94.8/83.0/65.8 も
`evals/score-index.jsonl` も根拠にならんと判明した）。

崩れ方は毎回同じ形やった:

| 崩れ方 | 実例 |
|---|---|
| 機械軸と LLM judge を1つの点数へ混ぜる | `script/model-ab-test.ts:244` の25点満点。判定不能が65% |
| 正規化してない軸を母集団を跨いで並べる | 「句反復 53.7% vs 4.5%」。長さ 892字 vs 94字の露出差が混ざる |
| 現象の違うものを同じ列に置く | 「空返信」に経路失敗（429/502）とモデルの空返答を混ぜる |
| 群を測定結果で切る | 「設定差 11.7倍」を、その群の median 字数で群を作って主張しとった |

## 合格の定義

```
機械軸 ─── 不良を落とすふるい。減点のみ。合格は出さん
            ↓ 通ったものだけ
「抜けたか」─ 合格判定。局長のみ。1軸だけ
```

機械軸は**合格を出さん**。出せるのは「これは不良や」だけ。

## 禁止事項（機構で守る）

| 規則 | 守っとる機構 |
|---|---|
| 長さは不足方向のみ見る。長い＝良いを採らん | `response-floor.ts` が本番の `resolveResponseFloor`（phase × 宣言設定 × 直前の user ターン長）の写しで、床を割っとるかだけを見る。上限は既存の `MAX_RESPONSE_PLAIN_CHARS` に任す |
| 長さ・水増し・反復を必ず同じ行に出す | `renderLengthVsSlopTable` が1行に並べる |
| 率は必ず分子と分母を持つ | `Rate` 型。`formatRate` が `20/482 = 4.1%` の形でしか出さん |
| 基準値が無関係な性質でズレる軸を入れん | `distinctRatio` は数える文字集合と同じ集合で割る。AI臭は per1000。反復は被覆率 |
| **不良は「その場面で不良」なものだけ数える** | AI臭の小道具（`filler_prop`）は erotic / climax でだけ数える。量だけ要求された場面の水増しやから不良なのであって、コーヒーの話をしとる会話ターンの `コーヒーの香り` は**その場の中身** |
| 機械軸に LLM judge を混ぜん | `axes.ts` は `src/lib/quality-guard.ts` の機械判定しか import せん |
| 母集団を跨いだ表を既定で出さん | `partitionForReport`。`--compare-sources` を明示せんと分かれたまま |
| 経路の失敗を不良として数えん | `summarize` が「error があり、かつ応答が1文字も無い」ターンだけを分母から外す。本文を出し切ってから落ちたターンは測る |
| 床は本番の式で出す | `response-floor.ts` の写しを `functions/api/__tests__/bench-response-floor-parity.test.ts` が本物と突き合わせる |
| 尻すぼみは途中終了と混ぜん | `detectTaper` が「宣言されたターン数に届いてへん会話」を分母から外し、残りをピーク比で判定する。**途中終了は有効ターン数と切り離して先に決める**（3ターン要求を入口に置いとった間、早期に落ちた会話が分子からも分母からも消えとった） |
| ある性質で群を切る時は、他の性質を揃えてから切る | 長さ四分位は**ターン位置・キャラ・phase・arm・宣言設定・モデルを揃えた層の中で**切る（`renderQuartiles`）。揃える物を増やすとセルが小さなるので、足りんかったら表を出さん。今のコーパスでは1層も残らん＝**長さの効果は測れてへん** |
| **一意な id を条件のラベルに使わん** | `generate.ts` の arm は `conditionArmOf` が宣言された設定（キャラ・モデル・max_tokens・温度・**実際に送るキャラシート本文**・出力形式の指示・台本）から導く。`--run`（一意なディレクトリ名）を arm にしとった間、同じ条件を何本回しても run ごとに別 arm になり、層（ターン位置 × キャラ × phase × arm × 宣言設定 × モデル）は**永久に n=1** で分位の3本・周辺率の8本へ構造的に届かんかった |
| 同じ値を別の群へ割らん | 四分位の境界は同じ字数の塊を割らん。割ると、四分位の差が長さやのうて並び順で決まる（全部同じ字数でも「順序のついた4つの箱」が出る） |
| **構造上ぜったい起きん物を「起きてへん」に数えん** | ターン間の軸は、比べる相手が在るターンだけで測る（1ターン目・前が全部空は null）。`axes` と `analyze` で同じ規則を使う |
| **除外の規則を出力にも書く** | `--jsonl` は `lengthCapped` と `afterBrokenContext` を毎行に出す。CLI が外した母集団を、読み手が規則を勘で再発見せんと作り直せるように |
| **測らんことと、無かったことにすることを分ける** | 壊れた文脈の後のターンは品質軸から外すが、経路失敗率の分母には残す。実際に飛んだリクエストやから。消すと失敗率が水増しされる |
| **同じ規則は全部の経路へ同時に当てる** | 経路失敗の切り方・configless の除外・履歴の切れ目は、`summarize` / **閾値感度** / 尻すぼみ / 四分位 / 限界再掲率 / 土台の点検の**全部**で同じにする。1箇所ずつ直しとった間、直してへん側が同じ嘘をつき続けた（この形で12回やらかした） |
| **対照は「比べたい物」以外を揃える** | 帰無分布のドナーは同じキャラ・同じモデル・同じ宣言設定の別会話に限る。揃えん物を跨ぐと、帰無側だけ似てへん本文になって差が水増しされる |
| **本番の「合格の境界」と「描ける境界」を混ぜん** | 不良軸は `checkXmlFormat`（合格判定＝`isXmlResponse`）に合わせる。文字数の勘定はパーサ側の境界でよい。一度これを取り違えて、**本番が弾く応答を合格に数えとった** |
| 送ってへん契約と照らして不良を数えん | 分量の指示を出さん run は `lengthDirective: false` を記録し、`benchFloorFor` が床を返さん（`isTooShort` は null＝分母から外れる） |
| 測れんかったものを「不良やない」に混ぜん | 帰無分布のドナー無し・四分位の標本不足・セル0個・ピーク比を出せん会話は、全部「推定でけへん」と印字して分母から外す |
| 上限切れをモデルの欠陥と混ぜん | `finish_reason: "length"` を記録して別列に出し、不良軸と尻すぼみの分母から外す（max_tokens はこっちの設定） |
| **表には出典のコマンドを書く** | `doc/bench-conditions-*.md` の各表の上に `出典: pnpm bench:score --source ... --group-by ...` を置く。行のキーだけで照合して差し替えた時に、**別の source の表**を貼ってもうた（§4 に生成 run のターン別表が入っとった）|
| doc の数字は手計算せん | 集計は `bench:score`、帰無分布・四分位・限界再掲率は `bench:analyze`。どちらもリポジトリに在る |
| **軸を触ったら数字を全部回し直す** | 手計算せんだけでは足りん。実装を直した時に古い出力を残すのは、手計算と同じだけ間違う。doc と PR 本文の両方を、その場で起こし直す（2回やらかした） |
| 生成が壊れた文脈へ入ったら会話を止める | `generate.ts` が上限切れ・撮り直し尽き・空応答で break する。続けると user 発話が2連続した会話を測る |
| 壊れた文脈で生成された本文は測らん | `dropTurnsAfterTransportFailure` が、経路失敗の後に返ってきた**本文のあるターン**を捨てる。落ちたターン自体は経路失敗率のために残す |
| 実測値の golden を置く | `.work/e2e-results/` の510ファイルは main に追跡済みで CI にも在る。`corpus-golden.test.ts` が実測値を固定し、軸を触ったら落ちる。**golden も CLI と同じ前処理（`markTurnsAfterBrokenContext`）を通し、生成 run も読む**（除外が効いとることを示す実証拠はそこにしか無い）。**軸を変えた時は表と golden を一緒に直す**（初版の「CI に無いので golden にでけへん」は誤りやった） |

## 軸

| 軸 | 中身 | 使っとる既存 export |
|---|---|---|
| 空返信 | 画面に出せる中身が1文字も無い | `hasReadableResponseContent` |
| 長さ（不足のみ） | **本番と同じ床と同じ測り方**（床が1300字未満なら生の response.length、以上なら可視文字数。quality-guard.ts:107）を割っとるか | `countUiVisibleChars` ＋ `response-floor.ts`（式は `resolveResponseFloor` の写し。parity テストが本物と突き合わせる） |
| 日本語の壊れ | 簡体字マーカー / BMP外CJK | （簡体字の集合は `quality-guard.ts:132` と同じ。「会」「将」は入れん） |
| 水増し（ターン内） | 再掲を差し引いた実質字数 / 差し引かん実質字数。1.0 が無水増し | `countDistinctContentChars` |
| 反復（ターン間） | 3本に分ける。下の表 | `findCrossTurnRepetitionMatch` / `findNearDuplicateMatch` |
| AI臭 | 辞書ヒット / 1000字 | `ai-slop-dictionary.ts`（唯一の新規辞書） |
| 感覚チャンネル | 具体描写の広さ（0-5） | `scoreSensualSpecificity` |
| 構造の壊れ | パーサ経由と正規表現のみの2経路が食い違う | `parseXmlResponse` + `countVisibleCharsIndependently` |

### 反復を3本に分ける理由

| 軸 | 何を答える |
|---|---|
| `repeatProduction` | 本番のガードが止めたはずか（生XML同士で本番と同じ入力を渡す） |
| `repeatLayerAware` | bench の判定。層ごとに**全ブロック**を比べる（本番は最初の1ブロックしか見ん） |
| `repeatCoverage` | どれだけ再掲か。**履歴が伸びると単調に上がる**ので、ターン位置を揃えて読む |
| `repeatCoveragePrev` | 直前1ターンだけを相手にした被覆率。履歴の本数に依存せん |

## 敵対レビュー

`prompt/instructions/adversarial-review-with-codex.md` の要求は「別エンジンに反証させる」。
やり方は3つある。**codex は GitHub 側で動く**（ChatGPT Codex connector が
「draft を ready にした」「`@codex review` とコメントした」で走る）。コンテナに CLI が
無くても、PR を ready にすれば codex のレビューは通せる。
CodeRabbit は Free プランやと要約とウォークスルーだけで、行単位の指摘は出ん。
別コンテキストのエージェントは、数値主張やデータの筋を壊すのに向いとる。

2026-09-01 はこの3つを全部通した。上の訂正履歴の後半はその返答から出とる。

## 使い方

```bash
pnpm bench:score                                  # source ごとに分けて全部
pnpm bench:score --group-by config                # 宣言された設定（arm / responseLength）別
pnpm bench:score --group-by turn                  # ターン別（尻すぼみ）
pnpm bench:score --source bench-run               # 生成した新条件だけ
pnpm bench:score --jsonl .work/bench/out.jsonl    # 1ターン1行

pnpm bench:analyze                                          # 帰無分布・長さ四分位・限界再掲率
pnpm bench:generate --character sakura --turns 10           # dry-run。課金ゼロ
pnpm bench:generate --character sakura --turns 10 --spend   # 実発行（要 OPENROUTER_API_KEY）
pnpm bench:generate --character sakura --run smoke-2 --spend # 同じ条件の2本目（arm は自動で一致する）
pnpm bench:generate --condition after-adapter-change --spend # 条件を手で分ける（bench の外を触った時）
```

`bench:generate` は**本番のパイプラインやない**。本番は D1 から champion prompt variant を引いて
platform prefix を足し、品質ガードでリトライを回す。bench が送るのはキャラシートと出力形式の指示と
台本だけ。生成物を本番の応答と同一視したらあかん。

キャラシートは `script/seed.ts` と `drizzle/*.sql` を in-memory sqlite へ順に適用して組み直す。
D1 もサーバも要らん。手で写した固定文字列を置くと migration が進んだ時に黙って古くなる。

`--run` は**一意なディレクトリ名**、arm は**条件のラベル**で、別物。同じ条件を n 本積むには
`--run` だけ変える（arm は宣言された設定から導くので自動で揃う）。逆に、bench の外
（`buildMessagesForApi` など `src/` 側）を触った後で前の run と並べたないなら、`--condition` で
明示的に分ける。digest は bench が持っとる範囲しか覆わん。
