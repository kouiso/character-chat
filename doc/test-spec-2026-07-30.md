## 1. テスト種別定義

| 種別 | 定義 | 専門用語 |
|------|------|----------|
| 回帰テスト | 既存機能が壊れていないことを確認する自動テスト群 | regression test |
| 意地悪テスト | 不正・極端・攻撃的な入力や外部障害を与えて耐性を確認 | adversarial / robustness / fault-injection testing |
| モンキーテスト | ランダム・高速・意味不明な操作を繰り返し、クラッシュや状態崩壊を引き出す | monkey / random testing |
| UI/UXテスト | 画面構成、操作性、フィードバック、アクセシビリティ、レスポンシブを検証 | UX audit / usability test |
| ユーザストーリーテスト | 想定されるユーザー行動パターンを起点に、 end-to-end で価値が成立するか検証 | user journey / story test |

## 4. 受入基準（満点 100 点とする）

| カテゴリ | 配点 | 合格基準 |
|----------|------|----------|
| 回帰（CI + 自動スクリプト） | 25 | `pnpm lint/build/test/verify:*` 全部 green、Playwright 既存 spec 全 pass |
| Adversarial/Robustness | 20 | 高リスクケース（A2/B2/C2/D2/H2/G2）80% 以上が期待通り |
| モンキー | 10 | 5 分間ランダム操作でクラッシュ・メモリリークなし |
| UI/UX | 20 | 3 viewport で主要画面 screenshot 比較、P0 摩擦 0 |
| ユーザストーリー | 25 | Scenario A/B/C + BS-1/CS-1/DS-1 全て 100 点 or 許容範囲内 |

**「抜けるか」ルーブリク（満点 100 点）**:

| 指標 | 目標 | 測定方法 |
|---|---|---|
| 一人称維持率 | ≥ 95% | `quality-guard` wrongFirstPerson 検出回数 / 総ターン数 |
| Phase escalation 率 | conversation→intimate→erotic→climax の順序維持 | `scene-phase` 判定ログ |
| 拒否・説教率 | 0% | 応答内「AIです」「設定上」「できません」出現回数 |
| 画像・コミック一貫性 | キャラ外見・衣装・タグが 80% 以上一致 | VLM grader / 主観レビュー |
| 没入感（主観） | 最終判定重み 30% | テスト実行者レビュー |

**満点条件**: 全カテゴリで合格基準を満たし、かつ上記ルーブリクの総合点が 90 点以上。

## 5. 実行計画

### Phase 1: 環境整備（既存資産の活用）

- コスト確認: 本 phase は mock/ローカルのみ。0 コスト。
- `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm verify:local && pnpm e2e:smoke`

### Phase 3: Adversarial / Robustness
- コスト確認ゲート: 実 API を使う場合は累計コスト <$0.20 か確認。超過なら mock 異常系に切り替え。
- `pnpm tsx script/model-ab-test.ts`（異常系 case 追加）
- `quality-guard` 異常入力単体テスト
- NSFW filter 境界語テスト（`curl` または Playwright）
- 認証リプレイ・超長入力テスト

### Phase 4: モンキー
- コスト確認ゲート: 実 API 不使用 or 上限 $0.10 内。
- `pnpm tsx script/e2e/scenario/s5-monkey-kink.ts`
- Playwright 上でランダムタップ/キー入力を 5 分間（シード固定、trace 収録）

### Phase 5: UI/UX
- コスト確認ゲート: 0 コスト（Playwright + ローカル worker）。
- `pnpm tsx script/verify/solo-features.ts`
- `pnpm tsx script/verify/visual-smoke.ts`

### 8.1 観点チェック

| 観点 | 評価 | コメント |
|------|------|----------|
| 網羅性 | △ | 動画・音声・TTS は除外。カメラ機能がないためモック許可は該当せず。 |
| 可実行性 | ○ | 既存 `script/e2e`, `script/verify`, `e2e/*.spec.ts` を活用可能。 |
| コスト管理 | ○ | 実 API テストは枚数・ターン数を事前に定め、予算内に収める。 |
| 客観性 | △ | 「抜けるか」の主観評価がある。ルーブリク化でリスク軽減。 |
| 優先度 | ○ | P0/P1/P2 に分けて、まず完成を阻むリスクが高い項目から実行。 |

### 8.2 危険な盲点（プレモーテム）
1. **Scenario キャラの不在**: 現状 `char-tsukasa`, `char-mitsuki`, `char-azusa` がローカル D1 にないため、Phase 1 で seed しないとユーザストーリーが実行不能。
2. **実 API テストの課金**: チャット 8 ターン × 画像 4 枚 × コミック 4 コマ × 2 キャラ は、コミック 1 回あたり $0.02 程度だが、phase 毎のフォールバック・リトライで予想外に増える。
3. **モンキー・ランダム性**: 再現困難なバグを発見する可能性があるが、結果の再現性がない。シード値固定や trace 記録が必要。
4. **UI/UX 主観**: 一人称利用者（Isogai）の感覚を再現できない。AI judge（VLM / quality-guard）を併用する。
5. **モックの限界**: ローカル mock は正常系のみ。異常系・latency・QuotaExceeded 等は実 API または fault injection でしか再現できない。

### 8.3 改善後の仕様
- 上記 8.2 を「残存リスク」として 10. に移動。
- Phase 1 に scenario キャラ seed を明記。
- UI/UX にはルーブリクと screenshot 比較を追加。

## 9. 敵対レビュー（Critic ロール）

### Critic 反論 1: 「満点基準が曖昧」
- 「抜けるか」を受入基準に含めるのは主観すぎる。数値化すべき。
- → Proposer: 主観を排除できない。代わりに scenario A/B/C の quality-guard スコア、拒否率、一人称維持率を数値化し、最終判定は主観レビューで重み 30% に留める。

### Critic 反論 2: 「モンキー・テストは時間の無駄」
- 再現性がなく、失敗したときの原因特定に時間を食う。
- → Proposer: モンキーは優先度 P2 ではなく、5 分間限定・シード固定・trace 収録・失敗時は必ず最小手順を抽出する。時間配分を Phase 5 以降に抑える。

### Critic 反論 3: 「画像・コミック実 API テストのコストが不透明」
- Novita 画像 1 枚 $0.002 でも、失敗リトライ・4 コマ × 複数回は積み上がる。
- → Proposer: Phase 2 回帰後に「chat のみ real」→「画像 1 枚」→「コミック 1 回」の段階実行にし、コストログを逐次確認。予算 $1.00 を超えたら打ち切り。

### Critic 反論 4: 「Native / LP / backend の記述が adult-ai-app に合っていない」
- ユーザが horsemanager 汎用テンプレートを引用した疑い。adult-ai-app に Native / LP はない。
- → Proposer: adult-ai-app は PWA/Cloudflare Pages なので、Native = PWA on mobile browser / desktop = web on desktop / backend = Pages Functions として解釈。別リポジトリ対象の場合は本仕様書を基に別途拡張する。

### Critic 反論 5: 「PBI 作成が後回しになる」
- 「最後にまとめて PBI を立てる」とあるが、blocker 級はテスト中に直す。
- → Proposer: 7. に「blocker（次のテスト実行を止める）のみ Phase 中に並行修正。残りは Phase 7 で PBI 化。」を明記。
