# bench 条件表 — 既存29条件を軸ごとに並べる（2026-09-01）

`.work/e2e-results/` にある **1,042ターン**へ機械軸を当てた結果と、そこから新しく1条件を
生成して同じ軸で測った結果。数字はすべて次のコマンドで再導出できる。

```bash
pnpm bench:score --source vlong-dogfood --group-by config
pnpm bench:score --source vlong-dogfood --group-by responseLength
pnpm bench:score --source vlong-dogfood --group-by turn
pnpm bench:score --source model-ab      --group-by model
pnpm bench:score --source bench-run
pnpm bench:analyze                                       # 帰無分布・長さ四分位・限界再掲率
pnpm bench:analyze --source bench-run --bench-runs <dir>  # 生成した run を分析する
```

## 読み方の規則

- **合格を出す表やない。**不良を落とすふるいで、合格判定は「抜けたか」1軸だけ
- **長さは不足方向のみ。**床は本番と同じ式（phase × 宣言 responseLength）。
  直前の user ターン長は記録に無いので係数 1.0＝**緩い側**で測っとる
- **率は必ず分子と分母を持つ**
- **応答が1文字も出んかった経路失敗だけを不良軸の分母から外す。**本文を出し切ってから
  ストリームが落ちたターンは測る（実際に4件ある）
- **source を跨いで並べん**（`--compare-sources` を明示した時だけ、警告つき）

## 3. 「設定差 11.7倍」— 取り下げる

宣言設定で切り直しても、この表からは「responseLength が主因」と言えん。3つ崩れる。

**(a) 11.7倍という量を再現した表がどこにも無い。** 宣言設定で切ると very_long 1092.5 /
medium 344 = **3.18倍**。11.7倍は「run 別 median の最小と最大」の比で、条件の中身やない。

**(b) モデルと日付が完全共線。**

| responseLength | モデル | n | median字数 |
|---|---|---:|---:|
| very_long | deepseek | 360 | 1088 |
| very_long | qwen | **0** | — |
| medium | deepseek | 37 | 442 |
| medium | qwen | 69 | 329 |

`very_long × qwen` が **0セル**。very_long は全部 deepseek・2026-08-16/17、medium は
qwen 65%・2026-08-18。モデルを deepseek に揃えると **1088.5 / 442 = 2.46倍**で、
3.18倍のうち 0.7倍分は設定やのうてモデルか日付や。

**(c) 同じ設定の中の差が、設定間の差と同じ大きさ。**

| 比べ方 | 幅 |
|---|---|
| medium の中（phase17 147 〜 phase20 469） | **3.19倍** |
| very_long の中（phase14 762 〜 phase9 1500） | 1.97倍 |
| 設定間（モデルを揃えた後） | 2.46倍 |

**言えるのはここまで**: 宣言 responseLength と median 字数は**対応しとる**（モデルを揃えて 2.46倍）。
**それが効いとる、とは言えん。** very_long × qwen のセルが無く、deepseek へ揃えても
arm と日付が一緒に動く。同じ設定の中の arm 差（medium で 3.19倍）の方が大きいので、
この記録からは長さ設定・プロンプト・日付を分離でけへん。分離するには
**他を止めたまま長さだけ振った条件**が要るが、**いまの `bench:generate` では作れん。**
`--turns` は台本を何ターン目まで回すかで、会話の深さと履歴が変わる。`--max-tokens` は
打ち切りの天井で、長さの指示やない。本番で長さを決めとる指示は D1 から引く platform prefix
の中にあって、bench は持ってきてへん。**作るなら bench 側に長さの指示を1つ足して、
それを宣言設定として summary へ書く**所からになる。

## 5. 反復は測定の artifact やない（帰無分布で確かめた）

各ターンの前方履歴を、**同じキャラの別会話**の同じ位置までに差し替えて測り直す。
ドナーはその位置まで到達した会話に限る（途中終了した会話を使うと履歴が短くなって、
帰無側が不当に低く出る）。数字は `pnpm bench:analyze` が出す。

| | 実測（全ターン） | 実測（対照が取れた分） | 帰無（別会話・5回平均） |
|---|---|---|---|
| 句反復（8字2句） | 277/428 = 64.7% | 224/347 = 64.6% | 12.1% |
| 句反復（16字2句） | 120/428 = 28.0% | 94/347 = 27.1% | 0.3% |
| median 被覆率 | 0.0343 | 0.0321 | 0.0000 |

**帰無と比べるのは真ん中の列**（同じ母集団）。ドナーの居らんターンは帰無側の分母から
外れるので、実測だけ全ターンで出すと比較が偏る。

ドナーは**同じキャラ・同じ宣言設定で、履歴の phase とモデルの並びが同じ**別会話に限る。
phase を揃えてへんかった間、erotic の履歴が conversation の履歴に差し替わって、
語彙がそもそも重ならん対照を使うとった（対照を取れんターンが増えた代わりに、
帰無は下がった。揃えた方が差は**大きく**出た）。

分母は**比べる相手が在るターンだけ**。1ターン目（履歴が空）と、前が全部空やったターンは
構造上ぜったい反復せんので「反復してへん」証拠に数えん（vlong では 480 → 428）。

16字以上の句が2つ戻ってくることは、別会話相手ではほぼ起きん（0.1%）。
会話内の自己反復が本体で、露出量でも定型句でも説明でけへん。

### 長さとの関係（**測れてへん**）

長さ四分位は、**長さ以外を揃えた層の中で**切る（ターン位置・キャラ・phase・arm・宣言設定・モデル）。
今のコーパスでは、8件以上かつ字数が4通り以上ある層が**1つも無い**（480ターン全部が
層としては小さすぎる）。`pnpm bench:analyze` はここで表を出さず「四分位を出せん」と言う。

一括で切った時に出とった Q1 33.6% → Q4 83.2% は、**ターン位置との交絡**やった。
被覆率は前方履歴すべてとの比較なので後ろのターンほど当たりやすく、しかも後ろのターンほど
長い（turn1 は52会話中42本で最短）。ターン位置だけ揃えると被覆率は動かんくなり
（0.045 / 0.026 / 0.026 / 0.026）、arm と宣言設定まで揃えると層が残らん。

**「伸ばした分の何割が再掲か」も出せん。**キャラ × phase × arm × 宣言設定 × ターン位置で切ると、
推定に使えるセル（3ターン以上）が **0個**になる。前の版で書いた「0.291字」「0.4字」は
arm を混ぜて出した数字で、長さやのうて arm ごとのプロンプト差や日付を測っとった。**取り下げる。**

まとめると、**長さと反復の関係についてこの記録から言えることは無い。**
反復そのものが本物（帰無分布との差）であることだけが残る。

**この行から条件比較をしたらあかん。** 理由を4つ:

1. **分量の指示を送っとらん。**summary は `lengthDirective: false`。§3 が主役やと
   言うとる軸そのものが入っとらんので、「111字 vs 1092字」の差はその軸を含んだ差になる。
   不足を「—」で出しとるのもこれが理由（送ってへん契約と照らさん）
2. **n=4 は独立した4件やない。**1会話・1キャラ・1モデル・1台本の連続ターンで、
   実効サンプルは会話1本。「この1本ではこうなった」以上のことは言えん
3. **会話は turn4 で終わっとる。**turn5 が 429 で落ちて、そこから先の turn6〜10 は
   **返事が抜けた文脈**（user 発話が2つ続く形）で生成されとるので採点から外した。
   10ターン回したつもりの run が、実際に測れたのは4ターン
4. **反復 0 は「短いから」やない。**判定は完全部分一致で、測れた4ターンは
   conversation ×3（turn1-3）＋ intimate ×1（turn4。intent も servedPhase も intimate）。
   反復が積み上がる erotic〜climax（turn7 以降）へは**そもそも到達してへん**

`buildMessagesForApi` が `Do NOT narrate or write like a novel.` を注入することも効いとる
（`script/bench/generate.ts` の ADAPTER_INJECTED_REMINDERS）。ただし**毎ターンやない。**
`(userTurnCount - 1) % 3 === 0` なので、10ターンの会話なら user の 4・7・10 ターン目だけ
（chat-message-adapter.ts:260）。**測れた4ターンのうち、この指示が入ったのは turn4 の1回きり。**
残り3ターンが短いのをこの指示のせいにはでけへん。
