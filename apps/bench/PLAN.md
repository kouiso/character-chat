### 診断

**モデルが渋る → 機構を足す → 複雑さが増える → 何が効いたか測れん → また機構を足す。**
856コミット全部が「インフラができた」で終わって、「体感が変わって、それを測った」まで行っとらん。

### この計画の賭け

1. **渋らんモデル(Grok)を使えば、押し戻す機構は要らん。** 浮いた労力を記憶と文体に注ぐ
2. **RAG は必ず作る。ただし「効いた」を測れる形で作る。** 局長の指示どおり RAG は中核に据えるが、legacy の轍を踏まんように **A/B を通ってから既定 ON** にする
3. **測る線を最初に引く。** これが今まで一度も無かった

| 項目 | 決定 | 理由 |

| 新アプリ | `apps/tsumugi/`（名前は仮） | |
| **pnpm workspace は作らへん** | `apps/tsumugi/` は**自前の package.json と pnpm-lock.yaml を持つ独立ディレクトリ**。`pnpm-workspace.yaml` は置かん | 共有 lockfile を書き換えると既存の推移的依存の解決がズレて **既存 CI が赤くなる**リスクがある。局長「無理に共通化しないで並べてくれればいい」＝ workspace は要らん。git リポジトリが1つ＝ monorepo の要件は満たしとる |
| 共通パッケージ | 作らへん。legacy の `src/` を1行も import せえへん | 同上 |
| LLM | **OpenRouter 経由 `x-ai/grok-4.6`**（既存 `OPENROUTER_API_KEY`）。プロバイダ層は OpenAI 互換の薄い1枚 | 局長の指定。`https://api.x.ai/v1` へは baseURL と鍵の差し替えだけで移れる |
| 出力形式 | XML やめて **`{action, dialogue, inner}` の JSON**（Grok の structured output） | XML は出力形式やなく **UI の描画契約**（`use-paced-reveal.ts` の段階表示）。捨てると体験が落ちる。脆い形式を堅い形式に替えるだけ |
| **RAG の基盤** | **Vectorize は使わへん。D1 に埋め込みを持って Worker 内でコサイン総当たり**（characterId で絞るので1クエリ数百件） | 下記「Vectorize をやめた理由」参照 |
| 埋め込み・再ランク | Workers AI `@cf/baai/bge-m3`(1024次元) + `@cf/baai/bge-reranker-base` | 全部 Cloudflare・**無料枠内**（bge-m3 は 100万トークンあたり 1,075 Neurons、無料枠 1日1万 Neurons ＝ 1日930万トークン分） |
| 実行基盤 | Cloudflare **Workers**（静的アセット + Hono API、`wrangler deploy`） | Pages の「リポジトリのどこをビルドするか」問題を回避。既存 Pages 設定に触らん |
| DB | **新規 D1 `tsumugi-db`**。既存 `adult-ai-db` は**絶対にバインドせん** | 既存は `preview_database_id == database_id` ＝ プレビューが本番を直接書く |
| アバター画像 | **`public/avatars/` の202枚を新アプリの静的アセットにコピー**。R2 は繋がへん | バックアップの `r2-keys.txt` 62件は**全部 `images/<uuid>.jpg`（生成画像）で、`avatars/` は0件**。R2 にアバターがある保証が無いので依存せん。git にある202枚が確実 |
| NSFW | 否定も検閲もせん。**NSFW専用の配管を作らん** | 局長の方針そのまま |

### Vectorize をやめた理由

| 論点 | 中身 |
|---|---|
| 書き込みの反映遅延 | Vectorize は upsert 後すぐには引けん（非同期でインデックス再構築）。「さっき話したこと」が次のターンで引けんかったら、**記憶RAGの存在意義が消える** |
| ID 64バイト制限 | 公式 limits で確認。既存の characterId には日本語混じりの長いものがあり、`${characterId}:lore:${n}` が枠外に出る |
| 無料枠の天井 | 保存500万次元 ÷ 1024次元 = **約4,880本**。記憶が伸びると詰まる |
| メタデータindexの順序制約 | ベクタ投入**前**に作る必要がある。P1でETL → P3でRAG というプランの順序と衝突 |
| 代わりに D1 総当たりで足りる根拠 | 検索は常に characterId で絞れる。1キャラあたり数百件 × int8量子化(1KB/本) = 数百KB。legacy も同じ結論を出しとる（`rag/cosine.ts` のコメント）。**遅延ゼロ・費用ゼロ・制限なし** |

## ⚠ 既存ファイルに1行だけ足さなあかん

```js
// eslint.config.js の globalIgnores（現在 L17-30）
globalIgnores([ "dist", ".wrangler/", ".work/", …, "script/",
  "apps/",        // ← これ1行
]),
```

理由：`pnpm lint` は `eslint .` でリポジトリ全体を舐める。ESLint v9 のフラット設定は**ディレクトリごとの継承をせん**（ルート設定1本が全ファイルに効く）。`parserOptions.projectService` の `tsconfigRootDir` がルート固定なので、`apps/tsumugi/` に .ts を1個置いた瞬間に「どの tsconfig プロジェクトにも属さんファイル」としてハードエラー → **`task ci` が赤くなる**。

- 追記は**無視リストへの1行だけ**。既存ファイルの lint 結果は1件も変わらん（`task ci` の緑で確認する）
- `vitest.config.ts` の include はルート相対（`src/**` 等）なので `apps/` を拾わん。`tsc -b` も各 tsconfig の include が明示されとるので拾わん。**確認済み**
- 1行も触りたくないなら別リポジトリにするしかない ＝ monorepo 化の指示自体の取り下げになる。**推奨は1行足す**

## 1ターンの処理の流れ

```
ユーザー発話
   ↓
[1] フェーズ判定  雑談か、そうでないか
        ↓ 雑談なら RAG をスキップ（legacy が -11.9 → -2.4 に改善した唯一の修正がこれ）
   ↓
[2] 埋め込み  embed(直近のユーザー発話 + 直前のAI発話, 400字まで)   Workers AI bge-m3
   ↓
[3] 検索      D1 から characterId で絞って全件ロード → コサイン総当たり
                lore   上位12 / memory 上位20 / style 上位8
   ↓
[4] 再ランク  @cf/baai/bge-reranker-base で「質問 × 候補」を通し直す（無料枠内）
              ベクトル類似度は「話題が近い」しか見えん。答えの材料になるかを見るのは
              クロスエンコーダの仕事。RAG で一番効く工程がタダで手に入る
   ↓
[5] 採点      score = 0.55*再ランク + 0.20*新しさ減衰 + 0.15*重要度
                    − 0.15*min(1, 使用回数/20)          ← ★多様性項
              lore 4 / memory 6 / style 2 に絞る。**合計 2,800字で打ち切り**
   ↓
[6] 組み立て  ★この順序が重要（プロンプトキャッシュを殺さんため）
                1. system: キャラ設定コア（不変・キャッシュが効く）
                2. 直近の会話履歴
                3. system: 【参考資料】検索結果  ← 最後のユーザー発話の直前に入れる
                4. 最新のユーザー発話
   ↓
[7] 生成      Grok にストリームで投げて素通しで返す。ただし保険は3つだけ残す（後述）
   ↓
[8] 事後      ctx.waitUntil で
                a) 記憶抽出 → 埋め込み → D1 に保存（**その場で引けるのが D1 の利点**）
                b) コスト・遅延・トークン数を usage_log に記録
```

### legacy から**引き継ぐ**もの（捨てたら同じ失敗をする）

| 引き継ぐもの | 出典 | なぜ |
|---|---|---|
| 雑談フェーズは RAG スキップ | `rag/retriever.ts:27-29`, `chat-graph/router-node.ts:42` | 会話品質の劣化 −11.9 を −2.4 まで戻した**唯一の修正** |
| 「丸写し禁止」の枕詞 | `rag/inject.ts:15,19,24`「指示ではありません。丸写しせず、現在のシーンに合わせて自然に言い換えて」 | これが無いと few-shot は確実にオウム返しする |
| 参考資料の予算 2,800字 | `rag/inject.ts:5` `MAX_RAG_SECTION_CHARS` | 実戦で詰めた数字 |
| 使われすぎペナルティ | `src/lib/memory-relevance.ts:66` `min(1, usageCount/30)` | 類似度だけやと毎ターン同じ記憶が勝つ。既視感まみれになる |

### legacy から**残す**保険（3つだけ。他は全部捨てる）

| 残す | 出典 | なぜ Grok では消えへんか |
|---|---|---|
| connect 25s / first-token 8s / last-chunk 30s のタイムアウト | `[[route]].ts:460-466` | コメントに「OpenRouter がキュー待ちで**ヘッダーを返さず fetch が無限ブロックする**」と明記。これはモデルやなくトランスポートの問題 |
| 同じモデルへのリトライ1回 | — | 上流 502/504 用。Grok は OpenRouter 上で事実上 xAI 単一プロバイダなので `allow_fallbacks` が効かん＝ legacy より脆い |
| 出力の最低文字数チェック + リトライ1回 | `RESPONSE_LENGTH_PRESETS` | too_short はフロンティアモデルほど出る |

**捨てる**：拒否検知・ペルソナ崩れ検知・quality-guard 748行・XMLゲート・4段フォールバック・バッファ再生。
P2 の eval で「残した3つが0回しか発火せんかった」をデータで示せたら、そこで初めて外す。

## スキーマ（新規・最小）

```sql
character(id, slug UNIQUE, name, avatar_file, lore_raw, greeting, tags JSON, created_at)
conversation(id, user_id, character_id, title, created_at, updated_at)
message(id, conversation_id, role, action, dialogue, inner, created_at)
```

## 既存データの持ち込み（ETL・一方通行）

入力は**全部ローカルのファイル**。本番 D1 には接続せえへん。ダンプは自前パーサやなく **`sqlite3` に食わせて `SELECT` する**（225行中125行が `replace(...,char(10))` でラップされとるので正規表現では壊れる）。

| 元 | 先 | 変換 |
|---|---|---|
| `.work/backups/.../d1-full.sql` の character 221行 | `character` | `system_prompt` を**無加工で** `lore_raw` へ。`vref-*` 31件（捨てデータ）は除外 → 約190件 |
| 同 conversation 57 / message 543 | `conversation` / `message` | XML の外枠を剥がして `{action, dialogue, inner}` に。**assistant 334行のうち139行が XML 形式**（剥がさんと Grok が XML を吐き始める） |
| `public/avatars/` 202枚 | `apps/tsumugi/public/avatar/` | ファイルコピー。`character.avatar` の値と突き合わせ |
| `prompt/rag/glossary.jsonl`(28) `exemplars.jsonl`(8) | `doc_chunk(kind='lore')` | そのまま |
| `.work/seeds/scenarios/` の手キュレーション2本 | `doc_chunk(kind='style')` | 腐らせんために入れるだけ（下記参照） |

**記憶の見込み**: message 543行の内訳は user 204 / assistant 335 / system 6。1会話あたりユーザー発話は平均3.6ターンと浅い。ここから取れる記憶は**数百件のオーダー**。D1 総当たりで余裕。

**⚠ 文体お手本(style)の元ネタが足りひん。実データを数えた結果：**
- `evals/score-index.jsonl` 94件のうち **85点以上は0件**（最高80点）
- `.work/seeds/scenarios/` は A/B用の未採点30ターン（1本200字と短い）＋手キュレーション2本だけ。しかも2本とも**エロ描写**で、「普通の会話」を建てる P1〜P5 では使えん
- 過去ログ259ターンは Qwen / DeepSeek / Euryale の出力。**捨てようとしとるモデルの文体を Grok に教えることになる**

→ **P5 の style few-shot は、既存資産の発掘では成立せえへん。局長が実際に会話しながら押した 👍 でしか作れん。**
　 だから 👍/👎 ボタンは **P2 の必須要件**（あとから付ける飾りやない）。P5 の着手条件は「👍 が30ターン溜まったら」。

| 画面 | 中身 |

## フェーズ計画

**順序が一番大事。** legacy は856コミット全部が「作る」で終わって「効いたか見る」に行かんかった。だから **測る線を引くのを最初のフェーズにする。**

| # | やること | 完了の判定（実際に見るもの） |
|---|---|---|
| **P-1a** | **Grok を先に試す（コードは1行も書かん）**。legacy の `system_prompt` をそのまま抜いて、スクリプトから OpenRouter の Grok に直接投げ、同じ場面の legacy 出力と読み比べる。既存アプリには一切触らん | 並べた比較テキスト。**ここで Grok が明らかに勝っとらんかったら、この計画ごと考え直す**（確信度表 #15 = 40% を、何も作る前に上げるための工程） |
| **P-1b** | **正解データを作る**。ダンプの assistant 259ターンから60件を抽出し、こっちで👍👎の下書きを付けた状態で提示 → 局長は**直すだけ**（15分想定）。`eval/golden.jsonl` に固定 | 60件のラベル付きファイル。**これが無い状態で P2 以降に進まへん** |
| **P0** | `apps/tsumugi/` 雛形 → CF Workers に hello world をデプロイ。eslint 1行追記 | ① 本番URLのスクショ ② **`task ci` が既存アプリで通ったまま**であること |

## 検証のやり方

**評価を2つに分ける。ここが今回の一番大きな方法論の変更。**
今までは「会話の点数」しか無かったから、悪いときに *検索が悪いんか / モデルが悪いんか* を切り分けられんかった。

| 種別 | 測るもの | やり方 |
|---|---|---|
| **検索eval** | recall@k / MRR | `eval/retrieval-gold.jsonl` に「この質問ならこの記憶が出るべき」を手で30件。**LLM を通さんのでタダで何回でも回せる** |
| **生成eval** | キャラ一貫性 / 記憶の想起 / AI臭さ / 応答長 / 主体性 の5軸 | シナリオを流して採点。採点の甘さ対策として、**`golden.jsonl` の局長ラベルと突き合わせ**、rubric と人間評価がズレたら **rubric の方を直す** |
| **コスト** | 円/ターン、月累計 | `usage_log` から。ヘッダに累計USDを出す（ダッシュボードを見に行かんと分からん状態にせん） |
| **目視** | 実画面 | 各フェーズの完了報告に Chrome MCP のスクショを必ず付ける |

**PASS の基準は90点。** legacy は75点を PASS にしとった（10点を PASS にした行すらある）。そこは繰り返さん。

|---|---|---|
| 序盤（system 1,200 + 参考資料 1,500 + 履歴 1,300） | 約4,000 | **約 2.5 円** |
| 40ターン目（履歴が伸びる） | 約25,000 | **約 10 円** |

60ターンのセッションで **$2.5〜3.0**、月10セッションで **$25〜30/月**。
**回避したかったサブスクより高い。** しかも legacy は 1/15 の単価で既に 402（残高不足）を踏んどる（`[[route]].ts:1961` に「支払い可能な max_tokens を本文から読み直して再試行」の実装がある＝実際に踏んだ痕跡）。

だから **コスト管理は P0 からの必須要件**にする：

1. **プロンプトキャッシュを殺さん順序**（固定 system を先頭・参考資料を末尾）。legacy の `rag/inject.ts:40` は参考資料を system の**前**に置いとって、毎ターン prefix が変わってキャッシュが効かん構造やった。ここを直すだけで入力コストが数分の1
2. **履歴を無制限に積まん**。10ターン + rolling summary で打ち切る（40ターン目で10円になるのはこれが原因）
3. **既定は安い tier**（`x-ai/grok-4.3` $1.25/$2.5）。`grok-4.6` は「このターンだけ強い方で」ボタンにする
4. 日次トークン上限を Worker 側で強制（超えたら429）
5. `eval/history.jsonl` に**毎回コストも記録**して、品質と一緒に線で見る

埋め込み・再ランクは **0円**（Workers AI 無料枠：bge-m3 は 100万トークンあたり1,075 Neurons、無料枠1日1万 Neurons ＝ 1日930万トークン分）。

## プレモーテム

失敗する道を12本洗い出した（別途の敵対エージェントによる検証込み）。重いものから7本と対策。

1. **eval の土台データがゼロで、P2 の baseline が LLM の自己申告になる** → legacy と同じ「数字は動くが体感は変わらん」の再生産。
   - 実測: `message_feedback` は本番ダンプに4行、うち2行は重複、1行は画像エラーへの bad。**実質1件**。
   - 対策: **P-1b を必須の前工程にした。** 60件の人手ラベル無しで P2 に進むのを禁止条件にする。

2. **「Grok が機構を不要にする」が外れる** → 保険を全部捨てた状態で上流が詰まり、UI が無限に固まる。
   - 実測: `[[route]].ts:466` に「OpenRouter がヘッダーを返さず fetch が無限ブロック」、`:1961` に402の再試行実装。これはモデル由来やない。
   - 対策: **タイムアウト3種・同格リトライ1回・最低文字数チェックの3つだけ残す。** 発火0回をデータで示せてから外す。加えて **P-1a で何も作る前に Grok を読み比べる。**

3. **RAG を core に据えたが効かん** → P3〜P5 の3フェーズを使い切って体感が変わらん。
   - 実測: legacy の A/B は3回とも RAG が勝っとらん（v1 ON負け / v2 中断ラン混入 / v3 delta −2.4）。
   - 対策: **RAG は必ず作るが、on/off の A/B に通ってから既定 ON。** 通らんフェーズは既定 OFF のまま次へ。legacy が効かせるのに必要やった4点（雑談スキップ・丸写し禁止の枕詞・2,800字予算・使われすぎペナルティ）を全部引き継ぐ。

4. **ETL が「190キャラのプロンプト書き直し」になって数週間止まる**
   - 実測: `【キャラカード】` を持つのは221中67件（30%）。残りは自由記述の散文。ダンプの125行は `replace(...,char(10))` ラップで正規表現では壊れる。
   - 対策: **パースせん。** `system_prompt` を無加工1テキストで `lore_raw` に入れる。ダンプは `sqlite3` に食わせて `SELECT` する。

5. **コストが「サブスクを払わない」という目的そのものを壊す**
   - 実測: Grok は現行 Qwen の入力約15倍。月$25〜30。legacy は 1/15 の単価で既に402を踏んどる。
   - 対策: キャッシュを殺さんプロンプト順序 / 履歴10ターン打ち切り / 既定を `grok-4.3` / 日次上限を Worker で強制 / 累計USDをヘッダ表示。**`usage_log` を P0 から入れる。**

6. **style few-shot のコーパスが、捨てようとしとるモデルの出力**
   - 実測: 過去ログ259ターンのうち139行が Qwen/DeepSeek 由来の XML。score-index に85点以上は0件。
   - 対策: **P5 の着手条件を「👍が30ターン溜まったら」にした。** 過去ログの発掘では作らん。

7. **`apps/` を足しただけで既存の `pnpm lint` が壊れる**
   - 実測: `globalIgnores` に `apps/` 無し + `eslint .` + `tsconfigRootDir` ルート固定。
   - 対策: 1行追記を明示的に承認事項として出した。加えて **pnpm workspace を作らんことで lockfile 共有のリスクも消した。**

## 敵対レビュー

**批判側の主張（これが一番痛い）**：
> 「お前の証拠は『アプリが悪い』やなく『測定が壊れとった』としか言うてない。それやったら一番安い手は、既存アプリの eval を直してモデルを Grok に差し替えることや。6フェーズの新規開発は、また『インフラを作って終わり』を繰り返すだけ。856コミットと同じ轍やないか」

**設計側の応答**：
1. 局長の指示が「monorepo 化して新しく建てる／既存には手を入れない」と明示されとる。既存の eval を直す＝既存に手を入れる、で指示と正面衝突する。
2. 技術的にも、legacy で Grok を試すには `ALLOWED_MODELS`（`src/lib/model.ts`）にモデルを足す必要があり、それ自体が既存改変。さらに quality-guard・拒否検知・XMLゲートが挟まるので、**Grok 素の実力が測れん**。測りたいものが機構に隠される。
3. **ただし批判の核は正しい。** 「作る前に測れ」は受け入れる。

**合意した修正（批判側の指摘を実際に取り込んだ）**：
- **P-1a を新設した。** legacy の system prompt を抜いてスクリプトから直接 Grok に投げ、legacy 出力と読み比べる。**コードは1行も書かん・既存にも触らん・数時間で終わる。** ここで Grok が勝っとらんかったら、6フェーズに入る前に計画ごと考え直す。
- **P2 の★ゲート**（legacy本番 vs 新アプリ を同一60件で比較）を、通らんと P3 以降に進めん構造にした。
- RAG を「core・mandatory」から「A/B を通ったら既定 ON」に降格した。

**相互に合意した最終見解**：
> 新アプリを建てること自体は指示であり前提。争点は「どこまで作ってから測るか」やった。
> P-1a（何も作らずに Grok を読み比べ）と P2★ゲート（60件で legacy と直接比較）の2枚を入れたことで、
> **最悪でも「数時間 + P0〜P2」で撤退判断ができる**。批判側の懸念は解消。両者合意。
