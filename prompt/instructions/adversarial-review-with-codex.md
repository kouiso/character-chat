# 品質チェックは Codex の敵対レビューを通す

自分の変更を自分の観点だけで見ると、想定した経路しか踏まん。品質を判定する時は
Codex に反証させてから結論を出す。

理由: 提案した本人が採点すると出来レースになる。反証は別のエンジンにやらせる。

## WHEN / THEN

WHEN 次のいずれかを行う
- PR を出す前の最終確認
- 「直った」「動いた」「合格」と判定する
- 計測の土台になるコード（ハーネス、採点、ゲート）を変更する
- 結果保証行為（マージ、完了宣言、外部への品質主張）

THEN Codex へ敵対レビューを投げ、返ってきた指摘を潰すか、成立せん理由を示してから進む。

```
mcp__codex-mcp-bg__codex
  approvalPolicy: "never"  sandbox: "read-only"  effort: "high" 以上
  cwd: リポジトリのルート
```

## 投げ方

- **反証を求める。** 「レビューして」やのうて「これを壊せ。既定は『間違っとる』」と書く。
- **主張を具体的に列挙する。** 何を正しいと言い張っとるかを箇条書きで渡す。曖昧な依頼は曖昧な返事になる。
- **file:line と再現手順を要求する。** 再現でけへん指摘は使えん。
- **読み取り専用で走らせる。** レビューに書き込み権限は要らん。
- 同意だけの返事は合格やない。反証を試みて失敗したことが合格の条件。

## 指摘の扱い

- NEVER 指摘を無視して進む。潰すか、成立せん理由を証拠つきで書くかの二択。
- NEVER Codex の自己申告を証拠として採用する。指摘された箇所は自分で開いて確かめる。
  詳細は [codex-orchestration](../../.claude/rules/codex-orchestration.md) と同じ扱い。
- 指摘が正しかった場合は、直した上で「戻すと落ちる」ことまで確認する。

## Detection

- PR を出した AND Codex の敵対レビューを通してへん = VIOLATION
- Codex が指摘を返した AND 潰しても反証してもへんまま進んだ = VIOLATION
- 「問題なし」の返事だけで合格にした（反証を試みた形跡が無い）= VIOLATION
